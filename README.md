# cspm-triage

[![CI](https://github.com/vNAUMv/cspm-triage/actions/workflows/ci.yml/badge.svg)](https://github.com/vNAUMv/cspm-triage/actions/workflows/ci.yml)

A command-line tool that turns [Prowler](https://github.com/prowler-cloud/prowler) scan results
(OCSF JSON) into a short list of what actually needs attention. It filters findings, applies
accepted risks that each have an owner, a reason and an expiry date, compares two scans
(new, persisting, resolved, gone), and writes a Markdown report. Its exit codes are designed for
a CI gate. Python 3.11+, standard library only.

Why: the raw FAIL count is a poor metric. Across four scans of a real AWS account, the FAIL count
went from 58 (scan 1) to 64 (scan 3), while the findings needing attention went from 14 to 0 by
scan 4. Fixes create new findings, and some findings are accepted on purpose; triage and diff are
what make the numbers meaningful.

## Quickstart

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

# Triage the sanitized sample scan (fake data). Exit 1: findings need attention.
cspm-triage triage tests/fixtures/sample_scan.ocsf.json

# The same, with the example accepted risks applied. Still exit 1: one finding is accepted, three remain.
cspm-triage triage tests/fixtures/sample_scan.ocsf.json --exceptions config/exceptions.example.toml

# Compare two scans. Exit 0: nothing new.
cspm-triage diff tests/fixtures/sample_scan.ocsf.json tests/fixtures/sample_scan.ocsf.json

# Write a report to a file instead of stdout.
mkdir -p reports && cspm-triage triage SCAN.ocsf.json --output reports/triage.md
```

A one-line summary, including where the accepted risks came from, always goes to stderr.

the CLI from the sample scan:

```sh

  --exceptions config/exceptions.example.toml --today 2026-06-15 --redact-account \
  --output docs/sample-triage-report.md
```

The diff report has one section per category (new, persisting, resolved, filtered out,
accepted, gone), each with a reason: for example "regression", "exception ended" or
"likely fixed". Empty sections are omitted.

## CLI reference

`cspm-triage triage SCAN` and `cspm-triage diff BASELINE CURRENT` take the same options:

| Option | Default | Meaning |
|---|---|---|
| `--exceptions FILE` | `config/exceptions.toml` if it exists | Accepted-risks file. An explicit path that does not exist is an error. |
| `--status LIST` | `FAIL` | Comma-separated statuses to report: `PASS`, `FAIL`, `MANUAL` |
| `--min-severity LEVEL` | `low` | `critical`, `high`, `medium`, `low` or `informational` |
| `--today YYYY-MM-DD` | today | Date used for exception expiry; set it for reproducible output |
| `--output FILE` | stdout | Write the report to a file; the directory must exist |
| `--redact-account` | off | Replace account IDs with `<account>` (see [Security design](#security-design)) |

Unknown severities and statuses are never silently dropped: they are kept and reported as
warnings. Unknown severities sort above Critical, because OCSF has levels above Critical.

| Exit | `triage` | `diff` |
|---|---|---|
| 0 | no finding needs attention | nothing new, no persisting finding got more severe, no expired exception |
| 1 | at least one finding needs attention | a new finding, a persisting finding whose severity increased, or an expired exception |
| 2 | usage or input error, including an empty scan | same |

Why this suits a CI gate:

- **A broken run never passes.** An empty scan usually means Prowler failed (expired
  credentials, a crash), so it is exit 2, not a clean result or a sea of "resolved" findings.
- **Silent changes fail.** In a diff, a severity increase or an expired exception would otherwise
  show up only as "persisting" plus a warning.
- **Wrong config is visible.** The stderr line always names the exceptions source, including
  `none (config/exceptions.toml not found)`, so a run from the wrong directory shows in CI logs.

## Accepted-risks file

A TOML file of `[[exceptions]]` tables; see
[config/exceptions.example.toml](config/exceptions.example.toml). Copy it to
`config/exceptions.toml`, which is gitignored.

```toml
[[exceptions]]
check_id = "iam_user_hardware_mfa_enabled"
resources = ["arn:aws:iam::123456789012:user/example-user"]
reason = "Break-glass user; virtual MFA accepted until hardware keys arrive"
owner = "security-team@example.com"
expires = 2027-03-31
```

| Field | Required | Meaning |
|---|---|---|
| `check_id` | yes | Prowler check ID (exact match) |
| `resources` | no | Glob patterns on resource UIDs; every resource of a finding must match. Omitted: the whole check is accepted. |
| `region` | no | Exact region match |
| `reason`, `owner` | yes | Why the risk is accepted, and who is accountable |
| `expires` | yes | A TOML date. Applies up to and including that date; afterwards the exception is ignored and reported as a warning. |

The first matching exception in file order wins. Unknown or missing keys are an error (exit 2)
that names the file and the entry number.

## Security design

- **Real data stays out of git.** Scan files (`*.ocsf.json`, except test fixtures), the real
  exceptions file and `reports/` are gitignored. The test fixture was built with
  [scripts/sanitize_fixture.py](scripts/sanitize_fixture.py), which reads real values only from
  its input and refuses to write if an original value or an unknown 12-digit number remains, or
  if it finds an AWS access key ID. A test checks that the only 12-digit number in the fixture is
  the fake account ID.
- **Report text is untrusted.** Resource names, details and exception fields can be set by anyone
  with access to the account or the config, and Markdown renderers produce HTML. Every such value
  is escaped (`&`, `<`, `>`, and Markdown characters that could open links, code spans or table
  cells), or put in a code span only when it contains no characters that could break out of it.
  Remediation links are links only for plain `https://` URLs.
- **`--redact-account` removes account IDs only.** It replaces the scans' account IDs and any
  other standalone 12-digit number with `<account>`, and refuses to write a report in which one
  remains. User, role, trail and bucket names, IP addresses and other identifiers stay in the
  report; the report header says so.
- **CI** ([ci.yml](.github/workflows/ci.yml)): ruff, pytest on Python 3.11 and 3.14, bandit,
  gitleaks over the full git history, and a smoke test of the installed CLI's exit codes.
  Third-party actions are pinned by commit SHA and updated by Dependabot; the gitleaks binary is
  verified by SHA-256. The workflow has `contents: read` permissions and uses no secrets.

## Known limitations

- **Exceptions match resources, not individual findings.** Some checks emit several findings for
  one resource (one per attached policy, for example); a resource-scoped exception accepts all of
  them together.
- **A diff uses one date and one exceptions file for both scans.** An exception that expired
  between the two scan dates is not detected: it is either active for both scans or expired for
  both.
- **Placeholder resources change UID.** Some checks report a placeholder resource (such as
  `detector/unknown`) while a feature is off and the real resource once it is on. The old finding
  then shows as "gone" with the hint "likely fixed", never as resolved.
- **Tested on AWS scans only** (Prowler 5.47.0, OCSF 1.5.0). Short resource names are derived from
  ARNs; other UIDs are shown in full.
- Development tool versions (pytest, ruff, bandit) are not pinned yet.

**Planned:** Jira tickets for Critical and High findings; an HTML report.

## How this was built

Built with an AI coding agent (Claude Code), plus a second AI assistant for planning and review,
with every command and file edit approved by hand,
work split into stages that each started with a plan I approved, and project rules in
[CLAUDE.md](CLAUDE.md). Moments where review or real data changed the result:

- **The diff key.** My fallback idea (check + region + resource) was disproved by two real scans:
  one check emits a finding per attached policy on the same resource. Findings are matched by
  Prowler's finding UID, which the same comparison showed to be stable across scans.
- **Fail-open caught in review.** An empty current scan would have shown every finding as "gone",
  which looks like a big improvement. It is now an error (exit 2).
- **Validation against an outside reference.** Triage results on a real scan were compared with a
  hand count (58 FAIL by severity): exact match.
- **A green check is not enough.** CI passed on the first run, so I verified it wasn't vacuous:
  gitleaks scanned 10/10 commits, the 3.11 job really ran CPython 3.11, and the smoke job was shown
  to fail when an expected exit code was changed on purpose.
- **Data handling as a rule.** After the agent printed a real resource ID, a CLAUDE.md rule limited
  it to reading real scans only when asked and printing counts and check names only.

The full log, including what went wrong, is in [AI_NOTES.md](AI_NOTES.md).
